### 2026-04 清理记录

- **删除废弃的 4 阶段 pipeline 探索**：block_splitter / format_spec_library /
  item_unifier / meta_extractor / relation_builder（全都是 untracked 状态，
  不被 orchestrator 主线调用）
- **删除废弃的处理器**：docx_processor / csv_processor / mineru_processor /
  pdf_processor / content_validator / cross_page_detector / md_parser /
  metrics / ocr_repair / sampling / stage

  已接入 `cli/generate.py`；`variant/evolve/solve-deep` 仍是 Post-MVP 占位。
- **删除 JSON 文件后端时代的索引**：storage/enhanced_index, index, tag_trie

  strategies / evolution 等模板均在 `prompts/templates/` 下，由 `templates.py` 加载。
- **精简 core/models.py**：删除 13 个只被废弃代码引用的死模型

  CorrectionResult / TaxonomyPath / TagSet / QualityAssessment / ItemSource /
  ItemProcessingResult + SubjectDomain / EducationLevel / PedagogicalLevel 枚举）

  两份与 `recognize_in_batches` 高度重复的遗留实现

## 3. 编码规范

| 规则 | 说明 |
|---|---|
| Python 版本 | 3.11+（`match`、`X \| Y` 联合类型、`StrEnum`） |
| 模型定义 | 统一 Pydantic v2 BaseModel，定义在 `core/models.py` |
| 类型注解 | 所有函数签名必须有 |
| 行宽 | 100 字符 |
| 格式化 | `uv run ruff format src/ tests/` |
| 检查 | `uv run ruff check src/ tests/` + `uv run mypy` (strict) |
| 命名 | 文件 snake_case, 类 PascalCase, 常量 UPPER_SNAKE |
| 日志 | 用 structlog，**禁止** print / logging 模块 |
| Prompt | 必须存为 `.txt` 文件，**禁止**内联到 Python 字符串 |
| Tag 格式 | 每段 `english:中文`，一个条目的 tags 是有序段列表代表一条根→叶路径 |

## 5. 配置管理

`AppConfig`（`config/settings.py`）使用 pydantic-settings，支持环境变量（`SCIFORGE_` 前缀）和 `.env` 文件。

### 5.1 关键 Pipeline 配置项

| 配置项 | 默认 | 说明 |
|---|---|---|
| `data_dir` | `data` | 数据根目录 |
| `checkpoint_dir` | `data/checkpoint` | Pipeline checkpoint |
| `pages_per_batch` | 5 | Phase A 每批页数 |
| `extract_window_lines` | 500 | Stage1Extract 初始窗口行数 |
| `extract_max_window_lines` | 3000 | Stage1Extract 扩窗口上限 |
| `pipeline_stage_queue_size` | 2 | 各 stage 间 queue 大小 |
| `pipeline_queue_size` | 4 | Producer-Consumer queue 大小 |
| `stage1_extract_max_retries` | 3 | Stage1Extract LLM 调用重试次数 |
| `vlm_max_retries` | 3 | Phase A batch 重试次数 |
| `tag_tree_max_depth` | 4 | 注入 prompt 的 tag 子树最大深度 |
| `tag_tree_max_nodes` | 200 | 注入 prompt 的 tag 子树最大节点数 |
| `vlm_dpi` | 200 | VLM 渲染 DPI |
| `vlm_max_concurrent` | 3 | VLM 并发上限 |
| `max_concurrent_files` | 8 | 目录模式下并发 logical_document 数 |

### 5.2 LLM 任务配置

通过 `[tasks.<task_name>]` TOML 段或 `SCIFORGE_TASK_<TASK>_<FIELD>` 环境变量。

Pipeline 主线使用 `vlm_convert` / `extract_and_classify` / `review` / `tag` /
`annotate_review` 五个可独立配置的 task（Stage3 无 LLM）。

## 6. 日志系统

structlog 结构化日志：
- **console** 模式（开发）：彩色可读
- **json** 模式（批量/生产）：JSON 行

CLI 全局开关：`sciforge --log-level DEBUG --log-format json`

日志级别使用指南：
- DEBUG: LLM prompt / 单步 buffer 状态
- INFO: 阶段完成、batch 入库、checkpoint 保存
- WARNING: 可恢复问题（重试中、incomplete 等待）
- ERROR: 操作失败（batch 重试用尽、save_batch 失败）

## 8. 实现顺序（v8 重构：5 阶段并发）

```
M1  数据模型 + schema v7 → core/{models.py, sentinel.py} / storage/{schema.sql, sqlite_backend.py}
M2  LLM schemas + retry → pipeline/{llm_schemas.py, retry.py with_feedback}
M3  Prompt 重写         → pipeline/{extract_stage1_*.txt, annotate_stage2_*.txt}
M4  5 个 Stage 实现     → pipeline/stages/{stage1_extract,stage1_review,stage2_annotate,stage2_review,stage3_persist}.py
M5  Orchestrator 重写   → pipeline/orchestrator.py（asyncio.gather 6 Task）
M6  配置 + CLI          → config/settings.py / cli/parse.py / pipeline/resume_state.py
M7  cleanup             → 删除 task1_extractor/task2_annotator/format_spec/extraction_metrics
M8  端到端验证          → uv run sciforge parse run --restart + 断点恢复
M9  文档 + 测试         → ruff/mypy + Docs/ + pytest
```
