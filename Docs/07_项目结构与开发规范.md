# 项目结构与开发规范

> 当前基线：Pipeline v11 / 内容库 schema v14 / QGen durable Harness / Web Chatbox。
> 详细行为分别以 `Docs/01`、`Docs/21`、`Docs/22`、`Docs/08` 和 `Docs/12` 为准。

## 1. 顶层目录

```text
MathForge/
├── AGENTS.md                  # Agent 协作、安全与验收约束
├── CLAUDE.md                  # 当前代码架构与常用命令
├── README.md                  # 产品入口
├── pyproject.toml             # 包、依赖、ruff/mypy/pytest 配置
├── uv.lock
├── config/

│   └── taxonomy.json          # 受控 taxonomy
├── Docs/                      # 当前契约、设计背景与参考资料
├── src/sciforge/              # 可发布 Python 包
├── tests/                     # 与 src 分域对应的测试
├── scripts/                   # 审计/运维辅助脚本
```

`data/`、`Raw Data/`、`.env`、`.venv` 不属于源码交付。原始资料和运行库不能为让测试通过而
手工改写；需要测试数据时在 pytest 临时目录构造最小 fixture。

## 3. 模块边界

### 3.1 Pipeline 与 Agent

| 维度 | Pipeline | Agent/QGen |
|---|---|---|
| 工作单元 | logical document / block / item | 一次生成、求解或评估请求 |
| 编排 | asyncio queue、背压、SENTINEL | StateGraph；可选 DurableQGenHarness |
| 状态 | 每文档 `state.json` + stage mirror | runtime SQLite checkpoint/event |
| LLM 优化 | adapter、批量提取/标注、风险 review | prefilter、候选上限、失败定向 evolve |
| 输出 | 来源条目、概念、评价、review | 题目、解答、验证、难度与 lineage |

不要把 pipeline stage 机械包装成 Agent，也不要让 QGen 直接绕过 storage quality gate 读取 SQLite。

### 3.2 四类数据库

- `sciforge.db`：教育内容与治理；
- `conversations.db`：消息、run link、artifact；
- `qgen_runtime.db`：run/step/checkpoint/event；
- `saas.db`：tenant/user/key/usage/task/behavior。

跨库用稳定 id 和 reconciliation 协调；不要尝试模拟跨 SQLite 全局事务。

## 4. 新功能落点

1. 新领域：先在 `disciplines/specs` 定义 type/form/tag/prompt 变量，再写契约测试；
2. 新输入格式：实现有界 adapter/recognizer 与 source locator，不在 orchestrator 写格式分支；
3. 新 pipeline LLM 任务：通过 `LLMClient`、`.txt` prompt、窄 Pydantic schema 和 retry feedback；
4. 新 Agent：定义 Input/Output，继承 `BaseAgent`，经 `from_config()` 统一绑定安全配置；
5. 新验证器：输出四态 `VerificationEvidence`，明确 applicable/required，不能用异常代表通过；
6. 新 API：在 schema 中建请求/响应，在 app factory 注入依赖，先鉴权/租户/质量过滤再 limit；
7. 新持久副作用：设计稳定幂等键、恢复 reconciliation 和失败事件；
8. 新 schema：同时更新 `schema.sql`、逐版本 migration、模型、round-trip 与 future-version guard。

## 5. Python 与类型规范

- Python 3.11+，Pydantic v2，mypy strict，Ruff line length 100；
- 公共函数与跨模块结构必须有完整类型；避免无边界 `dict[str, Any]`；
- 路径使用 `pathlib.Path`，数据库与文件资源用 context/finally 关闭；
- async 代码不得执行阻塞 I/O；必要时使用 `asyncio.to_thread`；
- 不使用进程全局可变业务状态；上下文显式传参；
- SQL 必须参数化，动态列名来自 allow-list；
- 不记录 API key、密码、完整 bearer token、raw chain-of-thought 或未截断用户代码输出。

## 6. Prompt 与 LLM 规范

- prompt 只放 `src/sciforge/prompts/templates/**/*.txt`；
- 静态 system 与动态输入分离，便于 cache；
- 每次结构化调用必须有 Pydantic schema 和包含验证错误的 retry feedback；
- 低风险确定性任务不能因为“方便”新增 LLM；
- 先批量、剪裁上下文与选择适当模型，再提高并发；
- tool calling 只能调用 allow-listed tool，代码执行遵守 sandbox policy；
- provider-specific 参数只在 capability/backends 层处理。

## 7. 数据与安全规范

- 不修改 `Raw Data/`；
- 不在代码、TOML、测试快照或日志硬编码 secret；
- ZIP/JSON/表格/图片先做资源上限；
- 不信任的 Python/Lean 默认 restricted container，缺 runtime 返回 unavailable；
- hosted API 必须 tenant scope；foreign id 与 missing id 返回相同 not-found 边界；
- 非 accepted、非 active concept、open review 或低分 item 不进入默认生成/推荐/组卷；
- 生成结果只有验证与 materialization 完成后才成为题库题目。

## 9. 开发与提交流程

```bash
uv sync --extra all
uv run pytest <相关测试>
uv run ruff check src tests
uv run ruff format --check src tests
uv run mypy
uv run pytest
```

在 `dev` 或 `codex/*` 功能分支工作，使用 Conventional Commits。提交只包含同一逻辑单元；
不得覆盖用户已有修改。代码变更必须同步当前契约文档，但历史设计文档应加“历史/路线图”标记，
不要伪装成已实现。

## 10. 完成定义

“完成”至少包括：

1. 实现与配置默认值一致；
2. 相关单元/集成/恢复/权限测试通过；
3. Ruff、格式与 mypy 通过；
4. schema、生成产物或前端状态经过实际读取/浏览器验证；
5. 当前文档没有虚构节点、事件、命令或版本；
6. 工作树只包含授权范围内的改动并按逻辑提交。
